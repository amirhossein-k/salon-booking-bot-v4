# نسخهٔ ورسل + MongoDB

این بسته نسخهٔ جدید مخصوص Vercel است، نه همان اجرای Docker/systemd قبلی.
ربات با **Webhook** کار می‌کند؛ رزروها، مراحل گفتگو، اعلان‌ها و مبالغ در MongoDB ذخیره می‌شوند.
تقویم شمسی، یادآوری مشتری و داشبوردهای دسکتاپ و موبایل حفظ شده‌اند.
توکن افشاشدهٔ قبلی عمداً در بسته نیست؛ ابتدا در BotFather آن را باطل و توکن تازه دریافت کن.

## قبل از شروع

MongoDB باید از **transaction** پشتیبانی کند: Atlas یا replica set/sharded cluster.
MongoDB تک‌سرور standalone برای این پیاده‌سازی قابل استفاده نیست.
داشتن دیتابیس به‌تنهایی کافی نیست: ورسل باید بتواند با TLS به آن متصل شود و کاربر دیتابیس مجوز لازم داشته باشد.
اسکریپت آماده‌سازی، این شرط را بررسی می‌کند؛ قبل از فعال‌کردن ربات آن را اجرا کن.
این بسته به حساب Vercel یا MongoDB شما متصل نشده و روی سرویس واقعی آزمایش نشده است.

## ۱. تنظیمات سالن

بسته را باز کن. پوشه‌ای که `app.py` و `vercel.json` دارد، ریشهٔ پروژه است.
فایل `config.example.json` را به `config.json` کپی و نام‌ها، شناسه‌های کارکنان و ساعات واقعی را وارد کن.
اگر تنظیمات واقعی نسخهٔ قبل را داری، همان `config.json` را استفاده کن.
نام‌ها و ساعت‌های نمونه، اطلاعات تأییدشدهٔ سالن نیستند.

شناسهٔ مدیر نمونه: `622650522`.
هر آرایشگر باید ربات را Start کند، /id بفرستد و عددش در `telegram_id` ثبت شود.
تا زمانی که شناسه وارد نشده، مدیر برنامه را مدیریت می‌کند اما آن کارمند اعلان اختصاصی و پنل ندارد.
مدت خدمت در `duration_minutes` و قیمت اختیاری به تومان در `price_toman` تنظیم می‌شود.
قیمت نامشخص را `null` بگذار؛ مبلغ واقعی توسط مدیر پس از انجام خدمت ثبت می‌شود.
ساعت‌ها تهران؛ روزهای هفتگی: ۰ دوشنبه تا ۶ یکشنبه.
تعطیلی موردی از پنل کارمند با مسدودکردن روز/بازه انجام می‌شود؛ تغییر ساعات هفتگی از فایل و deploy مجدد است.
شناسهٔ خدمت/آرایشگر را بعد از ثبت نوبت حذف یا عوض نکن.

## ۲. اتصال MongoDB را خصوصی آماده کن

یک دیتابیس اختصاصی مانند `salon_booking` انتخاب کن؛ اتصال به دیتابیس نامرتبط خودت را بدون بررسی استفاده نکن.
بسته collectionهای `bookings`, `blocks`, `sessions`, `guards`, `counters`, `outbox`, `audit`, `updates` ایجاد می‌کند.
داده‌های دیگر را حذف نمی‌کند، اما اگر همین نام‌ها در دیتابیس شما کاربرد دیگری دارند باید دیتابیس جدا انتخاب کنی.
این نسخه با ساختار دلخواه collectionهای موجود سازگار نیست و دادهٔ قبلی را خودکار حدس نمی‌زند.
یک کاربر دیتابیس اختصاصی با دسترسی readWrite روی همین دیتابیس بساز؛ حساب مدیر کل دیتابیس را استفاده نکن.
برای آماده‌سازی، کاربر باید مجوز ایجاد collection و index در همین دیتابیس را داشته باشد.
رمز URI با نویسه‌های خاص باید طبق قواعد MongoDB URL-encode شود.

در Atlas، Network Access را مطابق IP/مسیر خروجی سرویس تنظیم کن.
ورسل ممکن است IP خروجی ثابت نداشته باشد؛ به وضعیت پلن و امکانات شبکهٔ خودت توجه کن.
دسترسی `0.0.0.0/0` را راه‌حل بی‌خطر فرض نکن؛ دسترسی محدود/شبکهٔ امن اولویت دارد.
اگر ناچار به IP عمومی گسترده شدی، TLS، رمز تصادفی قوی، کاربر محدود و پایش اجباری‌اند.
این بسته TLS را برایت پیکربندی نمی‌کند؛ از URI امن ارائه‌دهنده، مثلاً `mongodb+srv://...` استفاده کن.

## ۳. آماده‌سازی دیتابیس، روی کامپیوتر خودت

Python 3.12 پیشنهاد می‌شود؛ دستورات را از ریشهٔ پروژه اجرا کن:

```bash
python -m venv .venv
```

محیط را فعال کن، سپس:

```bash
python -m pip install -r requirements.txt
```

مقادیر واقعی را در `.env` خصوصی وارد و در محیط ترمینال بارگذاری کن؛ بسته فایل `.env` را خودکار نمی‌خواند.
در لینوکس/macOS، پس از کپی `.env.example` به `.env` و ویرایش:

```bash
chmod 600 .env
set -a
. ./.env
set +a
python scripts/init_db.py
```

در ویندوز، متغیرهای محیطی همان نام را در PowerShell تعریف کن؛ برای URI حاوی `$` از کوتیشن تکی استفاده کن.
رمز را در چت، فایل گیت یا اسکرین‌شات منتشر نکن.
برای Windows می‌توان مقدار حساس را با `Read-Host` در همان ترمینال وارد کرد.
اگر اسکریپت اعلام کرد standalone پشتیبانی نمی‌شود، باید دیتابیس را به replica set یا Atlas تبدیل کنی.
هر بار آرایشگر جدید با شناسهٔ جدید اضافه می‌کنی، قبل از فعال‌کردن رزرو او این اسکریپت را دوباره اجرا کن.
اسکریپت قابل تکرار است و شمارنده/نوبت‌های موجود را صفر نمی‌کند.

## ۴. متغیرهای Vercel

در پروژهٔ Vercel، Settings → Environment Variables، این‌ها را برای **Production** وارد کن:

| نام | مقدار |
| --- | --- |
| BOT_TOKEN | توکن جدید BotFather |
| MONGODB_URI | URI خصوصی MongoDB |
| MONGODB_DB | نام دیتابیس اختصاصی، مثلاً salon_booking |
| TELEGRAM_WEBHOOK_SECRET | رشتهٔ تصادفی حداقل ۳۲ نویسه |
| CRON_SECRET | راز متفاوت و تصادفی حداقل ۳۲ نویسه |
| CSRF_SECRET | راز سوم تصادفی حداقل ۳۲ نویسه |
| DASHBOARD_USER | نام ورود مدیر، مثلاً manager |
| DASHBOARD_PASSWORD | رمز اختصاصی تصادفی حداقل ۱۶ نویسه |
| DASHBOARD_ADMIN_ID | شناسهٔ مدیر تعریف‌شده در config.json |

برای ساخت هر راز جدید در محیط خودت:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

هر بار فرمان را جدا اجرا کن؛ همهٔ رازها را یکی نگذار.
Webhook secret فقط از حروف انگلیسی، عدد، `_` و `-` تشکیل شود.
`PUBLIC_BASE_URL` فقط برای اسکریپت محلی ثبت Webhook است.
رازهای Production را به Preview یا مخزن Git نده.
Preview با دیتابیس واقعی می‌تواند دادهٔ واقعی را تغییر دهد؛ برای staging دیتابیس و ربات جدا بساز.
در این بسته webhook/cron روی deploymentهای غیر Production ورسل مسدودند، اما داشبورد staging همچنان به تنظیمات خودش وصل می‌شود.
بعد از تغییر Environment Variables دوباره deploy کن.

## ۵. انتشار روی ورسل

کد را در یک مخزن خصوصی Git قرار بده، سپس در Vercel آن را Import کن.
فایل `.env` و داده/بکاپ SQLite را commit نکن؛ `.gitignore` همراه بسته آماده است.
`config.json` حاوی برنامه و شناسهٔ کارکنان است؛ در مخزن خصوصی بماند و شامل رمز نباشد.
Framework برای این نسخه FastAPI است؛ ورسل `app.py` و متغیر `app` را شناسایی می‌کند.
Root Directory همان پوشهٔ `app.py` است. برنامه را با `python bot.py` یا Docker اجرا نکن.
`requirements.txt` وابستگی‌ها را نصب می‌کند و `vercel.json` سقف اجرای ۶۰ ثانیه را مشخص می‌کند.
اگر پلن/تنظیمات حساب سقف متفاوت دارد، مقدار را مطابق محدودیت واقعی حساب تنظیم کن.

بعد از deploy، `/health` باید پاسخ `ok: true` بدهد؛ این فقط بررسی روشن‌بودن endpoint است،
نه تضمین اتصال دیتابیس. ورود و `/api/report` و یک رزرو آزمایشی باید جدا بررسی شوند.
داشبورد مدیر: `https://YOUR_PROJECT.vercel.app/`
داشبورد موبایل: `https://YOUR_PROJECT.vercel.app/mobile`
نام و رمز مطابق Environment Variables هستند.

اگر Vercel Deployment Protection روشن است، تلگرام و زمان‌بند بیرونی ممکن است به endpointها نرسند.
برای Production یک تنظیم پشتیبانی‌شده بساز که `/api/telegram` و `/api/cron` قابل دسترسی باشند؛
این دو مسیر در خود برنامه با راز مستقل محافظت می‌شوند.
راز bypass حفاظت ورسل را به URL عمومی یا چت اضافه نکن.
داشبورد همچنان با Basic Auth و HTTPS محافظت می‌شود؛ برای سامانهٔ عمومی بزرگ، مدیریت نشست،
rate limit و حساب‌های مستقل مدیر نیاز به توسعهٔ بیشتر دارند.

## ۶. Webhook تلگرام را ثبت کن

نسخهٔ polling قدیمی ربات را خاموش کن؛ برای یک توکن دو پردازش/روش هم‌زمان اجرا نکن.
در ترمینال خودت همان `BOT_TOKEN` و `TELEGRAM_WEBHOOK_SECRET` که در Production وارد کرده‌ای را قرار بده.
متغیر `PUBLIC_BASE_URL` را روی آدرس ثابت Production تنظیم کن، نه URL هر Preview.
سپس:

```bash
python scripts/setup_webhook.py
```

اسکریپت Webhook را روی `/api/telegram` تنظیم می‌کند، با یک اتصال هم‌زمان و بدون حذف پیام‌های منتظر.
تغییر توکن یا دامنهٔ Production نیاز به ثبت دوبارهٔ Webhook دارد.
توکن در آدرس قابل مشاهدهٔ مرورگر یا مخزن کد قرار نمی‌گیرد.
بعد از ثبت، در تلگرام /start بفرست و یک رزرو آزمایشی کامل انجام بده.

## ۷. یادآوری و تلاش مجدد اعلان‌ها: این مرحله الزامی است

یادآوری‌ها مستقل از پیام‌دادن مشتری باید اجرا شوند؛ فقط Webhook برای آن‌ها کافی نیست.
مسیر کارگر: `/api/cron` با درخواست GET و هدر:

```text
Authorization: Bearer YOUR_CRON_SECRET
```

در **Vercel Hobby** فایل پیش‌فرض همراه بسته Cron ندارد.
یک زمان‌بند بیرونی که درخواست HTTPS با هدر خصوصی را پشتیبانی می‌کند، هر دقیقه این مسیر را صدا بزند.
برای زمان‌بند بیرونی، secret را در تنظیمات خصوصی هدر ذخیره کن، نه query string یا لینک عمومی.
اگر خودت سرور لینوکسی داری، نمونهٔ cron دقیقه‌ای:

```bash
curl --fail --silent --show-error --max-time 55 \
  -H "Authorization: Bearer $CRON_SECRET" \
  "$PUBLIC_BASE_URL/api/cron"
```

توجه: اجرای cron سیستم باید متغیرها را از فایل خصوصی بارگذاری کند؛
متغیرهای ترمینال تعاملی خودکار وارد cron نمی‌شوند.

در **Pro/Enterprise**، `vercel.pro.example.json` را به‌جای `vercel.json` قرار بده و deploy کن؛
Cron دقیقه‌ای فعال می‌شود و Vercel مقدار `CRON_SECRET` را در هدر Bearer می‌فرستد.
فایل Pro را روی Hobby کپی نکن؛ زمان‌بندی دقیقه‌ای آن طبق محدودیت Hobby قابل deploy نیست.
فقط یکی از زمان‌بند بیرونی یا Vercel Cron کافی است.
Cron دقیق تضمینی نیست؛ کارگر صف محدود است و تعداد زیاد اعلان نیاز به پایش/افزایش ظرفیت دارد.

پیش‌فرض یادآوری مشتری: ۲۴ ساعت و ۲ ساعت قبل؛
`reminder_minutes: [1440,120]`، مهلت جبران `reminder_grace_minutes: 30`.
رزرو بعد از موعد یک یادآوری، یادآوری گذشته را دریافت نمی‌کند.
یادآوری بعد از شروع یا پایان مهلت جبران ارسال نمی‌شود.
وضعیت لغو درست قبل از ارسال دوباره بررسی می‌شود؛ پیام از قبل تحویل‌شده پس گرفته نمی‌شود.
در هر اجرای زمان‌بند حداکثر ۲۰۰ نوبت واجد شرایط به‌ازای هر فاصله بررسی می‌شود.
هر اجرای کارگر حداکثر ۳۰ اعلان با بودجهٔ زمانی کوتاه ارسال می‌کند؛ برای یک سالن کوچک طراحی شده است.
خطای شبکه/تلگرام در صف می‌ماند. دریافت اعلان توسط آرایشگر نیاز به Start قبلی دارد.

## دیتابیس و هم‌زمانی

هر تغییر تقویم در transaction ابتدا guard اختصاصی آرایشگر را می‌نویسد، سپس تداخل را بررسی می‌کند.
دو رزرو/تعطیلی هم‌زمان یک آرایشگر به‌خاطر write conflict با snapshot تازه بررسی می‌شوند.
کل نتیجهٔ یک پیام تلگرام، تغییرات جلسه و اعلان‌ها با هم commit می‌شوند.
update_id تلگرام در دیتابیس ثبت می‌شود تا retry معمولی، رزرو تکراری نسازد.
این شناسه‌ها پس از ۳۰ روز با TTL حذف می‌شوند؛ این حذف روی نوبت‌ها اثر ندارد.
عملیات شبکهٔ تلگرام داخل transaction نیست تا retry تراکنش پیام تکراری تولید نکند.
کارگر اعلان‌ها lease دارد؛ تحویل همچنان «حداقل یک‌بار» است:
قطع اجرا درست پس از ارسال و قبل از ثبت تحویل می‌تواند پیام تکراری ایجاد کند.

## دادهٔ نسخهٔ قبلی

این بسته SQLite را خودکار به MongoDB منتقل نمی‌کند.
اگر قبلاً مشتری واقعی در نسخهٔ قبلی رزرو کرده، آن دیتابیس را پاک نکن و قبل از جایگزینی
برای مهاجرت کنترل‌شدهٔ رزروها، مبالغ، محدودیت‌ها و شناسه‌ها برنامه‌ریزی کن.
در این نسخه رزروهای MongoDB از ساختار collectionهای معرفی‌شده خوانده می‌شوند، نه ساختار دلخواه قبلی شما.
تا زمان مهاجرت، استفاده از این بسته با دیتابیس تازه یعنی نوبت‌های SQLite قدیمی دیده نمی‌شوند.

## آزمون‌ها و مرزهای اعتبار

تست‌های پایه روی SQLite فقط اعتبار رفتار قبلی را می‌سنجند، نه MongoDB.
تست‌های واحد Mongo در این محیط با درایور/collectionهای شبیه‌سازی‌شده اجرا می‌شوند.
آزمون اتصال واقعی، replica-set transactions، write conflict و deployment ورسل بدون سرویس واقعی انجام نشده‌اند.
برای نصب وابستگی‌های آزمون در کامپیوتر خودت:

```bash
python -m pip install -r requirements-test.txt
python -m unittest discover -s tests -v
```

برای آزمون واقعی یک دیتابیس **صرفاً آزمایشی** بساز و:

```text
TEST_MONGODB_URI=YOUR_PRIVATE_TEST_URI
TEST_MONGODB_DB=salon_test_vercel
```

سپس `python -m unittest discover -s tests -p 'integration_mongo.py' -v` را اجرا کن.
دیتابیس آزمایشی با دادهٔ ساختگی تغییر می‌کند، بنابراین اطلاعات واقعی سالن نباید در آن باشد.
این آزمون‌ها پیام تلگرام واقعی ارسال نمی‌کنند.
چک‌لیست قبل از مشتری واقعی: رزرو دو حساب در همان ساعت، رزرو مستقل آرایشگر دوم،
بستن ساعت، لغو با دلیل، دریافت اعلان، اجرای cron، ورود موبایل و ثبت مبلغ آزمایشی.

## حریم خصوصی

نام، تلفن، مراحل گفتگو، پیام صف و تاریخچه در MongoDB و پیام خصوصی تلگرام ذخیره می‌شوند.
شمارهٔ مشتری در داشبورد نشان داده نمی‌شود، اما پنل مجاز تلگرام آن را دارد.
رمزگذاری انتقال با TLS را بررسی کن؛ این برنامه field-level encryption یا حذف خودکار اطلاعات مشتری ندارد.
رضایت، سیاست نگهداری، دسترسی کارکنان و پشتیبان‌گیری MongoDB را خودت تنظیم کن.
ورود مدیر مشترک است و اصلاح مبلغ به `DASHBOARD_ADMIN_ID` نسبت داده می‌شود.
کد پایهٔ `core.py` و `dashboard.py` برای استفادهٔ مشترک منطق باقی مانده‌اند؛ مسیر واقعی ورسل
فقط `app.py`، `MongoStore` و `MongoAnalytics` است و SQLite یا فایل محلی برای ذخیره‌سازی باز نمی‌شود.
